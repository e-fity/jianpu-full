# 使用说明（jianpu_api 接口）

一张简谱图片进去，两张东西出来：

- `<图名>_overlay.png` —— 在原谱上**原位**把数字盖成字母（版式不动）；
- `<图名>_notes.json` —— 逐音对照表：**第几行 / 原始数字 / 转换后的字母**。

识别本身**一行没写**，全部复用 `D:\Letter piano11` 的 `jianpu2letter` 包
（`ocr_jianpu` 认谱、`overlay_letters` 盖字母、`mapping` 查键位）。
本模块（`jianpu_api.py`）只是个薄封装。

> 不想敲命令？有**网页版**：`python webapp.py`，然后开 http://127.0.0.1:8010/ ——
> 拖图进去、拖动对比看结果。详见第九节。

## 二、函数签名

```python
convert(image_path, outdir="out", *, title=None, key=None, meter=None,
        tempo=None, measure_mode="vline")  ->  (overlay_path, table_path, payload)
```

| 参数 | 说明 |
|---|---|
| `image_path` | 输入图片（`.png/.jpg/.jpeg/.bmp/.tif/.tiff/.webp`）。文件不存在 → `FileNotFoundError` |
| `outdir` | 输出目录，默认 `out/`，不存在会自动建 |
| `title` | 曲名。不给就**从页眉自动读**，读不到用图片文件名 |
| `key` | 调号。写 `F` 或 `1=F` 都行。不给就**从页眉自动读** `1=X`，读不到退回 `1=C` |
| `meter` | 拍号。**不自动读**，不给一律 `4/4`（跟 piano11 的规矩一致） |
| `tempo` | 拍速（四分音符/分钟）。不给就存默认 100，并把来源标成 `default`（见第四节）|
| `measure_mode` | `"vline"`（默认）按识别到的小节线切小节；`"beats"` 按拍数切 |

`title` 和 `key` **都给了**会跳过页眉 OCR。实测 7.png：默认 **21.6s** → **13.2s**。

返回值 `payload` 就是落盘那份 JSON 的 dict（不用再读一次文件），
`overlay_path` / `table_path` 是产物的路径。

> ⚠ **不是线程安全的**：OCR 的底图和缩放倍数存在 `ocr_jianpu` 的模块全局里
> （`_LAST_COLOR` / `_LAST_SCALE`），并行跑会把字母画到别人的谱上。
> 多张图请**串行**处理。

## 三、产物

### `<图名>_overlay.png`

原谱上**原位**替换：字母直接盖在原来数字的位置上。版式、歌词、减时线、附点、
延时线、连音弧、小节线**全是原谱像素**，一个都没重画 —— 所以"重排导致的错位"

|---|---|
| 字母 | 认出来并换掉的数字 |

| **红框** | 没认出来 / 疑似误判的位置（数字留在框里，等你人工核对） |

## 四、JSON 结构

真实片段（孤勇者，10.png）：

```json
{
  "format": "jianpu2letter-notes-v1",
  "title": "孤勇者",
  "key": "1=B",
  "meter": "4/4",
  "source": "D:\\Letter piano jk\\web_out\\6bec80e2c41d\\upload.png",
  "tempo_qpm": 65.0,
  "tempo_source": "manual",
  "scale": 2.823529,
  "counts": { "total": 377, "letters": 263, "rests": 114, "unknown": 0 },
  "lines": [
    {
      "line": 1,
      "notes": [
        { "line": 1, "index": 1, "n": 2, "o": 0, "letter": "D", "q": 0.5, "box": [349, 744, 32, 46] },
        { "line": 1, "index": 2, "n": 7, "o": -1, "letter": "M", "q": 0.5, "box": [425, 744, 33, 47] }
      ]
    },
    {
      "line": 3,
      "notes": [
        { "line": 3, "index": 1, "n": 7, "o": -1, "letter": "M", "q": 2.0, "box": [325, 1151, 34, 46], "lyric": "错，" },
        { "line": 3, "index": 2, "n": 0, "o": 0, "letter": "0", "q": 1.0, "box": [482, 1151, 32, 46] }
      ]
    }
  ]
}
```

> 每行的 `notes` 都是**截断过的**（第 1 行实际有 17 个音）。

顶层：

| 字段 | 含义 |
|---|---|
| `format` | 固定 `jianpu2letter-notes-v1` |
| `title` / `key` / `meter` | 曲名 / 调号 / 拍号 |
| `source` | 输入图片的绝对路径 |
| `tempo_qpm` | 拍速，**四分音符/分钟**。做视频的时间轴按它算 |
| `tempo_source` | `manual`=人填的 / `default`=没人填、用的默认 100 |
| `scale` | 识别时把原图放大的倍数（每个音的 `box` 就在这个空间里）|
| `counts` | `total` 总音数、`letters` 换成字母的、`rests` 休止、`unknown` 没认出来的 |
| `_instructions` | 字段自带的说明（就是下面这张表） |
| `lines[]` | 按行分组：`line`（行号）+ `notes[]` |

每个音：

| 字段 | 含义 |
|---|---|
| `line` | **第几行**（从 1 起） |
| `index` | 这一行的第几个音（从 1 起）。和 overlay 图上的 `L03N029`、`_review.json` 的 `id` 对得上 |
| `n` | **原始数字**：`0`=休止、`1..7`=唱名、`null`=没认出来 |
| `o` | 音区：`-1` 低音点 / `0` 中音 / `1` 高音点 |
| `letter` | **转换后的字母**键位。休止是 `"0"`，认不出是 `null` |
| `q` | 时值，**四分音符 = 1.0**（减时线每多一条减半、附点 ×1.5、延时线每条 +1）。做视频按它算秒数 |
| `box` | `[x, y, w, h]`，该音在**识别用缩放图**上的像素框（换算到原图尺寸要除以 `scale`）。画游标/高亮框靠它 |
| `lyric` | 这个音对应的歌词（多个字 = 一字多音/拖腔）。没有就不出现这个键 |
| `shift` | **只在需要时出现**：`"LSHIFT"` / `"RSHIFT"` |
| `unknown` | **只在 `n` 为 `null` 时出现**（`true`）|

`shift` 为什么要单独有：映射2 里 ±2、±3 音区没有独立的键，要靠按 Shift，
所以**字母相同、音区不同**时只能靠它区分。例：17.jpg 第 1 行第 3 个音是
`n=1, o=2`（实数据），按映射2 就是 `letter="E"` + `shift="LSHIFT"`。

`lyric` 有一个**已知缺口**：一行底下叠着多段歌词时，piano11 只留**最上面那一段**，
其余丢弃 —— 所以这里也只有第一段。而且反复记号不展开，所以"第几遍唱第几段"暂时无从谈起。

## 五、字母是怎么来的

`(n, o)` → 字母的换算直接调 piano11 的 `mapping.key_for`，本模块**没另写一套**，
不会和工具其它部分的字母对不上。映射2 的表：

| 数字 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| 低音 `o=-1` | Z | X | C | V | B | N | M |
| 中音 `o=0` | S | D | F | G | H | J | K |
| 高音 `o=1` | E | R | T | Y | U | I | O |

`o=±2` 用上面 ±1 的键 + 左 Shift；`o=±3` 用 + 右 Shift。

## 六、常见问题

**1. `ModuleNotFoundError: No module named 'cv2'`**
用错解释器了。见第〇节，要用 `D:\python\python11\python.exe`。

**2. `ImportError: 找不到 jianpu2letter 工程目录`**
`D:\Letter piano11` 不在位置上，设环境变量 `JIANPU_PIANO11` 指过去。

**3. 能并行跑多张图吗？**
不能，见第二节的警告。一张一张来。

**4. 认错了想改一处再重跑？**
这份 `_notes.json` 是**只读对照表**，**喂不回**工具（它没有
`_review.json` 那套时值/位置字段）。
要"改一处重跑"请走 piano11 自己的路：
`python -m jianpu2letter 图片.png -o out` 会出 `_review.json` + 它自己的 `_overlay.png`，
改完 JSON 再喂回去（详见那边 `使用说明.md` 第六节）。
本接口的定位是**快速拿到"数字↔字母"对照**，不是人工校正流程。

**5. overlay 会覆盖我的原图吗？**
不会。只往 `outdir` 写，原图一个字节都不动。

## 七、怎么确认结果没跑偏

**这条要小心：不能拿"和某个历史产物逐字节相同"当判据。** 我一开始就是这么验的（当时
`out/7_overlay.png` 确实和 `D:\Letter piano11\out\7_overlay.png` 逐字节相同），
但 2026-09-29 发现这个"相同"**只在那一天的代码状态下成立** —— 用户当天改了
piano11 的 `ocr_jianpu.py` / `overlay_letters.py` 之后，**两边同时变了**，那个哈希基线就作废了。
所以跟历史产物比，只能证明"代码没变"，证明不了"结果对"。

**能证明"本接口没碰坏原管线"的是这两条：**

1. **重复跑同一张图，产出必须逐字节相同**（本接口自己的确定性）：
   实测 7.png 连跑 3 次、单独跑 / 三张连跑、以及 `PYTHONHASHSEED` 取 0 / 0 / 12345，
   全部是 `4d171f865d64dfe9`。
2. **改了本接口的代码之后，`git diff` 里不能有碰到渲染链路的行** ——
   即 `overlay_letters.render` / `ocr_jianpu.ocr_to_stream` / 底图（`_LAST_COLOR`）
   这些调用一个字都不能动。纯往 JSON 加字段是安全的。

行号与数字序列可以和 `D:\Letter piano11\out\7_review.json` 逐行对照（这个只要
`save_review` 的分行规则没变就恒成立）。

## 九、网页版：传图看结果（`webapp.py`）

不想敲命令就用网页：

```bash
cd "D:\Letter piano11\jk"
python webapp.py
```

然后浏览器开 **http://127.0.0.1:8010/** ，把简谱图片拖进去（或点右上「上传图片」）。

**页面怎么用**：

| 页面上的东西 | 说明 |
|---|---|
| **中间那条竖线（或下方滑块）** | 拖动它，在**原谱 ↔ 已替换**之间来回对比。这是核对最快的方式 |
| 红色行 | 这个音**没认出来**（`n` 为 null），原位替换图上有红框 |
| 数字列 `?` | 同上 |
| 数字列 `0`、字母列 `0` | 休止；字母谱里没有键位，图上也就不换 |
| 字母的颜色 | 低音蓝 / 中音琥珀 / 高音绿 |
| 字母右上 `⇧` | 这个音要按 Shift（映射2 的 ±2/±3 音区） |
| 「下载 JSON」 | 存下逐音对照表（就是 `_notes.json`） |
| 「下载替换图」 | 存下原位替换图，想放大细看细节就点它 |

顺便：拖对比的那条线为什么能对齐 —— 因为原位替换图**和原图同尺寸**，两张图叠在同一个盒子里就是像素级重合。

**产物落在哪**：**两处** —— `web_out/<随机 id>/`（上传的原图 + 转换出的中间产物）和
**`out/`（曲库）**。页面上的图、JSON 链接**都指向曲库那份**，所以改完 4 项再点「下载 JSON」，
拿到的**一定是改过的那份**（同一份数据存两处、只更新一处，是这工程踩过最多的坑）。

**参数**：

```bash
python webapp.py --port 9000
```

```bash
python webapp.py --debug
```

**四点要注意**：

1. **一次只能跑一张**。识别用的底图和缩放倍数是 `ocr_jianpu` 的模块全局（见第二节的警告），服务端已经用锁**排队**，所以同时提交不会出错、只会等 —— 但同一时刻只有一张在跑。
2. **页面上能填曲名/调号/拍号/拍速** —— 上传前填好，或上传后在结果区改（**秒存，不重跑识别** —— 这 4 项不参与识别）。`title`+`key` 都填了会跳过页眉 OCR（快几秒）；留空就从页眉自动读，读不到退回文件名 / `1=C`。
3. 这是 **Flask 自带的开发服务器**，只监听 `127.0.0.1`，别拿它对外开。
4. **谱面尺寸规则：不放大，比栏宽还宽就缩到栏宽，高度不限**（所以高过一屏的谱会纵向滚动，右栏 sticky 一直可见）。为什么不"压到一屏看完"—— 量过全库 41 张，**38 张高过 900px**、最高 7016px；压到一屏会把 4.png 缩成 0.27×、23.png 缩成 0.10×，数字全糊。要看得更大就点「下载替换图」。
5. **红框的含义有两层**：`n` 为 null（真没认出来，表格里那一行会标红），**以及**"判成休止、但形状复核最像的不是 0"（疑似误判）。后者**不会**出现在表格里、也不计入 `counts.unknown` —— 它的 `n` 仍然是 0。所以**图上的红框可能比表格里的红字多**，以图为准。

**实测**（无头 Chrome + CDP 驱动，走**真实文件输入框**）：

| 项 | 7.png（516×754）| 1.jpg（1218×1620）|
|---|---|---|
| 曲名 / 调号 / 拍号 | 采蘑菇的小姑娘 / 1=F / 4/4 | 上海滩 / 1=C / 4/4 |
| 音数 | 366（328 字母、30 休止、**8 没认出来**）| 247（237 字母、10 休止、**0 没认出来**）|
| 表格行数 | 381（366 音 + 15 行标题）| 259 音 + 行标题 |
| 谱面显示 | **516×754，原生尺寸**（不放大）| 954×1269，缩到栏宽 0.78× |
| 横向滚动 | 无 | 无 |
| 每行高度 | 29px（全表统一）| 29px |

走网页不会改变识别结果 —— 网页和无头浏览器两条路走的都是 `jianpu_api.convert()`。
（**别用"和某个历史产物逐字节相同"来验这件事**，那会随 piano11 改代码而失效，见第七节。）

## 十一、视频：三种风格（`make_video.py`）

**三种风格共用同一条管线**（读 JSON → 排时间轴 → 逐帧画 → 合成主旋律 → mux 成 mp4），
**只有「画一帧」的函数不同** —— 所以加一种风格 = 加一个画帧函数 + 一个装配函数，
时间轴/音频/编码一行不动。

```bash
python make_video.py out/9_notes.json                    # 落块（默认），输出到 视频/
python make_video.py out/9_notes.json --style play       # 谱面跟弹
python make_video.py out/9_notes.json --style roll       # 小球下坡
```

| `--style` | 画面 | 输出后缀 |
|---|---|---|
| `tiles` | **落块音游**：7 车道，块高 = 时值，块底边碰「现在」线 = 该弹的时刻；块上挂歌词标签，最底部一条整句字幕带（当前字高亮）| `_试演奏.mp4` |
| `play` | **谱面跟弹**：上半 = 字母谱（默认）或原谱，粉色游标压在当前音上；下半 = **电脑键盘**，当前音要按的键按下去高亮 | `_跟弹.mp4` |
| `roll` | **小球下坡**：蛇形下坡楼梯，弹珠一路往右滚、碰到屏幕边缘换行反向；木板只降不升 | `_小球下坡.mp4` |

产物统一落在 **`视频/`** 子目录。

### 常用参数

| 参数 | 作用 |
|---|---|
| `--size 1920x1080` | 画幅（默认竖屏 `1080x1920`）|
| `--bpm` | 拍速；不给就用 JSON 里的 `tempo_qpm`，再没有就 100 |
| `--fps 30` | 帧率 |
| `--stills 10,45` | **只出静止帧**（按视频时长的百分比），不编码视频 —— 快速试版式用 |
| `--no-audio` | 不合成音频（只出画面）|

风格专属（默认值看 `--help`）：

| 风格 | 参数 |
|---|---|
| `tiles` | `--lookahead`（「现在」线上显示几秒 → 决定像素比例）、`--lyric-band`（底部字幕带高度比例，给 0 就不要字幕带）|
| `play` | `--page {overlay,source}`（上半屏用字母谱还是原谱）、`--split`（上下半屏比例）|
| `roll` | `--beat-px`（一拍多少像素）、`--drop-px`（旋律每跌一级往下走多少）、`--row-gap`（换行额外下降多少）、`--stair-top` |

### 音频

按 `n/o/key` **合成**主旋律：正弦叠 4 次谐波 + 衰减包络。
**不是钢琴音色**，也**没有伴奏**。音高换算：`1=C` → 主音 MIDI 60，`n` 取大调音级，`o` 给八度。

### 踩过的坑（每条都真栽过）

1. **中文必须用中文字体** —— 拿 `Arial` 画「现在」会得到两个豆腐块 `□□`
   （拉丁字体里没有汉字字形）。所以 `font()` 和 `cjk_font()` 是两个函数。
2. **`--second-px` 别照抄网页 app 的 288** —— 那个值是在它自己 650px 高的线上区域标定的
   （= 2.26 秒视野）。换到 1080×1920（线上 1382px）就变成 4.8 秒视野，谱子填不满、上方大片空白。
   现在按 `--lookahead`（视野秒数）反算。
3. **roll 的「每拍像素」固定、不跟 BPM 走** —— 跟着走时南泥湾（BPM 118）每拍只有 122px、
   半拍 61px，键位字母都挤不下。快歌画面走得快是对的，但**单位不能跟着变**。
4. **底部字幕带 ≠ 块上歌词标签**，两者都留：标签管"这个字是哪一下唱的"，
   字幕带管"整句唱到哪了"。字幕带放最底部、**不透明** —— 放「现在」线下面会挡块、
   而且半透明底透出块的亮边显得脏。
5. **`tiles`/`roll` 的配色常量是共用的** —— 删一种风格时**别照名字删常量**
   （`PLANK_*` / `BALL_*` 出现 3 次 = 定义 + 两种风格在用）。
6. **`视频/` 这个子目录名两边必须一致** —— `make_video.py` 的 `VIDEO_DIR` 和
   `webapp.py` 的 `_video_path()`，一边改一边不改就"渲出来了但页面说没有"。
7. **批处理跑的时候别改 `make_video.py`** —— 每首是独立子进程，改动会**逐首生效**，
   改到一半就是"前几首新代码、后几首半截代码"。
8. **批处理的日志要用 `python -u`** —— 输出重定向到文件时是块缓冲，`print` 全卡在缓冲区，
   看起来像"卡死了"，实际一直在跑。

## 十二、全量同步（`sync_corpus.py`）

**什么时候要跑**：改了 `D:\Letter piano11` 的识别代码之后。

识别代码在 piano11、产物在本工程的 `out/`，**两边没有版本绑定** —— 你改了识别代码，
已有的产物**不会跟着变**，还是旧代码的结果（2026-09-29 那次：48 处红框是旧判据的假警报，
重跑后才降到正常）。新加了图片**不用**跑这个（那是 `convert` 或网页上传的事）。

```bash
python sync_corpus.py --dry-run     # 只核对依赖签名 + 列出会重跑什么，不动文件
python sync_corpus.py               # 全库重跑
python sync_corpus.py 42 43         # 只重跑这两首
```

它做三件事：

1. **核对依赖签名** —— 本工程依赖 piano11 的那些调用（`overlay_letters.render` /
   `ocr_jianpu.ocr_to_stream` / `mapping.key_for` / 几个 `_LAST_*` 全局）。
   签名一变立刻报警 —— 否则问题会以"字母画错位置"这类现象在外面才暴露。
2. **重跑** —— 读每首 JSON 的 `source` 找回原图，重跑 `convert`，覆盖 overlay 和 JSON。
3. **报变化** —— 用"数 overlay 上的红框个数"当最省事的指标，打出 `红框 26 -> 1 ← 变了`。

**它保得住你手填的东西**：重跑只产「页眉读到的曲名/调号」+「默认 4/4、100」，
所以它会先把旧的 4 项读出来、重跑时传回去（`tempo` 只在原来源是 `manual` 时才沿用，
免得把"默认 100"误标成"人工填的"）。

**它不"只挑旧的跑"**：试过按"缺 `box`/`q`/`lyric` 字段"判新旧，但那只在**改数据格式**时有效；
下次改判据（字段不变、结果变）它就完全看不出来、报"全部都是新的"然后什么都不做。
**判别成本不可靠，重跑成本才是确定的**（18 首约 3 分钟）。

**踩过的坑**：它曾经**写错文件** —— `convert()` 的产物名取的是**源文件名**，而网页上传的歌
`source` 指向 `web_out/<id>/upload.*` → 名字变成 `upload` → 重跑把产物写进 `out/upload_*`、
自己那首**一个字节没动**（mtime 都不变）。当时 18 首里有 3 首歌词一直是 0，就是这个。
现在改成先写临时目录、再按曲库名复制。
